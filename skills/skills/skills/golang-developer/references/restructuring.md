# Restructuring an Existing Project to This Layout

Use this playbook when the user asks to migrate, restructure, reorganize, or "follow the golang-developer layout" on an existing Go codebase.

The single biggest failure mode is **creating the new tree without removing the old one** — the repo ends up with `service/`, `internal/services/`, *and* `src/service/` all coexisting, imports half-pointing each way, and nothing compiling. This document exists to prevent that.

---

## Golden Rules

1. **Move, never duplicate.** Every file should end up in exactly one place. Use `git mv` so history follows the file and so deletes/creates are recorded as a rename in one operation.
2. **Confirm the mapping before touching anything.** Print a table of `old path → new path` and get user approval. The cost of one round-trip is far smaller than the cost of unwinding a wrong bulk-move.
3. **Build after every batch.** `go build ./...` and `go vet ./...` after each logical group of moves. If you wait until the end, you'll have ten errors layered on top of each other and won't know which move caused which.
4. **Regenerate, don't migrate, generated code.** Files like `*.pb.go`, `*.pb.gw.go`, `wire_gen.go`, OpenAPI specs — delete them at the old path, fix the generator config, and re-run the generator at the new path. Moving them is always wrong because the `// Code generated by ... DO NOT EDIT.` paths will be stale.
5. **Delete empty dirs only after the build is green.** `find <old-roots> -type d -empty -delete` once tests pass. Empty dirs left behind invite people to re-add files to the wrong place.
6. **Never delete a file the user didn't authorize**, even if it looks unused. Flag it (`possibly orphaned: path/to/file.go`) and ask. The user may have in-progress work or know context you don't.

## Workflow

### Phase 1 — Inventory (do not move anything yet)

Discover what's actually there, not what you assume is there:

```bash
# Top-level shape
find . -maxdepth 3 -type d -not -path '*/\.*' -not -path '*/vendor*' | sort

# Entry points
find . -name 'main.go' -not -path '*/vendor/*'

# Go file distribution per top-level dir
for d in */; do echo "$d: $(find "$d" -name '*.go' 2>/dev/null | wc -l)"; done

# Generated / proto / wire
find . -name '*.pb.go' -o -name '*.pb.gw.go' -o -name 'wire_gen.go' 2>/dev/null

# Module path (you'll need this to fix imports)
head -1 go.mod
```

Categorize what you find into:
- **Business logic** (will move into `src/`)
- **Entry points / wiring** (will move into `engine/`, `injector/`)
- **Proto definitions** (will move into `proto/`)
- **Schema / migrations / seeders** (will move into `src/schema/`)
- **Generated code** (will be regenerated, not moved)
- **Tests** (mirror the move; the `test/` package convention applies)
- **Ambiguous** (ask the user)

### Phase 2 — Propose the mapping table

Output a table to the user *before* any move. Group by destination, mark confidence:

| Current path | → | Target path | Confidence |
|---|---|---|---|
| `internal/order/service.go` | → | `src/service/order_service_impl.go` | high |
| `internal/order/repository.go` | → | `src/repository/order_repository_impl.go` | high |
| `models/order.go` | → | `src/model/entity/order.go` | high |
| `handlers/order_handler.go` | → | `engine/grpc/controller/order_controller_impl.go` | **needs confirm** — looks gRPC, but also has http.HandleFunc |
| `api/proto/order.proto` | → | `proto/<svc>/admin/v1/order.proto` | **needs confirm** — admin/insider/public tier? |
| `pkg/utils/*.go` | → | `src/helpers/` (mostly) or `src/model/types/` (value types) | **needs confirm** per-file |
| `cmd/migrate/main.go` | → | `engine/goose/main.go` | high |
| `internal/order/*_test.go` | → | `test/service/order_test.go` | high |

Wait for the user to approve, edit, or push back. Do not move ambiguous files until they're confirmed.

### Phase 3 — Common-case mapping reference

Use this as your starting point. It's not exhaustive; lean on Phase 2 to surface anything that doesn't fit.

| Common convention | Target | Notes |
|---|---|---|
| `cmd/{name}/main.go` | `engine/{name}/main.go` | One subdir per process (`grpc`, `rest`, `routine`, `eco`, `goose`, `seeder`) |
| `internal/{domain}/service*.go`, `service/`, `services/` | `src/service/{domain}_service_impl.go` | One file per service; interface in same file or sibling |
| `internal/{domain}/repository*.go`, `repo/`, `repository/` | `src/repository/{domain}_repository_impl.go` | Fluent `For*` builders go here |
| `models/`, `entity/`, `entities/`, `domain/` (struct files) | `src/model/entity/` | Embed BaseEntity; never declare `TableName()` |
| `dto/`, `model/dto/` | `src/model/frame/` | DTOs (Bonus, Charge, Product, etc.) |
| `types/`, `pkg/types/` (value types only) | `src/model/types/` | AmountItem, MutatedValue, enums |
| `handlers/`, `controller/`, `http/` (gRPC handlers) | `engine/grpc/controller/` (or `grpc-insider/`, `grpc-public/`) | Pick tier per route auth level |
| `rest/`, `gateway/` | `engine/rest/` (or `rest-insider/`, `rest-public/`) | grpc-gateway code only |
| `api/proto/`, `protos/`, `pb/` (source `.proto`) | `proto/{svc}/{tier}/v1/` | Tier = admin/insider/public |
| `api/proto/*.pb.go`, `pb/*.pb.go` | **delete + regenerate** | Never move generated proto |
| `migrations/`, `db/migrations/` | `src/schema/migrations/` | Goose format |
| `seeders/`, `seeds/` | `src/schema/seeders/` | |
| `config/`, `configs/` | `src/config/` | Viper + Vault wrapper |
| `cache/`, `pkg/cache/` | `src/cache/` | Redis CacheManager |
| `nats/`, `events/`, `pubsub/` | `src/pool/` | NATS JetStream + Go channel pools |
| `clients/`, `integrations/` (outbound gRPC clients) | `src/provider/` | Outbound provider wrappers |
| `workers/`, `jobs/` (long-running) | `src/worker/` | PDF generation, product switching, etc. |
| `helpers/`, `util/`, `utils/` | `src/helpers/` | Shared utilities |
| `constants/`, `const/` | `src/constant/` | Config key constants |
| `logger/`, `log/` | `src/logger/` | Zap structured logging |
| `middleware/`, `middlewares/` | `src/middleware/` | gRPC & REST middleware |
| `wire/`, `di/` | `injector/inject/` | Wire ProviderSets |
| `wire_gen.go` | **delete + regenerate** at `injector/inject/wire_gen.go` | Never move |
| Anything in `pkg/` exposed for *other services* to import | `integration/{tier}/v1/` | This is the outbound SDK |
| All `*_test.go` files | `test/{layer}/{name}_test.go` | Separate test package convention |

### Phase 4 — Execute moves in batches

Order matters. Do leaves first, then things that depend on them:

1. **Constants, logger, config** — shared, low-coupling, nothing depends on each other internally.
2. **Entities & types** — `src/model/entity/`, `src/model/types/`, `src/model/frame/`.
3. **Repositories** — depend on entities.
4. **Services** — depend on repositories + entities.
5. **Proto source files** — move `.proto`, delete `.pb.go` / `.pb.gw.go`, regenerate.
6. **Controllers / transformers** — depend on services + generated proto.
7. **Engine entry points & Wire** — depend on everything; regenerate `wire_gen.go` last.
8. **Tests** — mirror final structure into `test/`.

For each batch:

```bash
# Move with git so history follows
git mv old/path/file.go new/path/file.go

# Update package declaration in the moved file if the new dir has a different package name
# (use grep to find them, Edit to fix — don't sed blindly across the repo)

# Update imports across the codebase. Module path stays the same, only the suffix changes:
#   old: github.com/org/svc/internal/order
#   new: github.com/org/svc/src/service
# Use goimports if available, or scoped find+sed with manual review.

# Verify
go build ./...
go vet ./...

# Commit per batch — easier to bisect later
git commit -m "restructure: move <layer> to src/<layer>"
```

If `go build` fails: **fix before moving on**. Do not stack the next batch on a broken build.

### Phase 5 — Regenerate

Once all source files are in place:

```bash
# Proto — ALWAYS via make protogen (runs buf lint → buf generate → protoc-go-inject-tag)
# Never call `buf generate` directly during a restructure — it skips inject-tag,
# silently wiping every `validate:"..."` tag on request messages.
make protogen

# Wire
make wire       # or: cd injector/inject && wire

# Goose migrations (if entity changes triggered new migrations)
make migrate-status
```

If any of these fail, the most common causes:
- `buf lint` failure at step 1 of `make protogen` → likely a stale `package` declaration in a moved `.proto` (e.g., file moved from `proto/old/order.proto` to `proto/svc/admin/v1/order.proto` but the `package` line still says `old`). Fix the `package` and `go_package` lines to match the new path.
- Stale `buf.yaml` / `buf.gen.yaml` pointing at the old proto root → update the `modules:` / `paths:` entries
- Wire `injector.go` `// +build wireinject` file still importing old paths → fix the imports there too
- A `ProviderSet` that listed concrete types from old paths → swap to new paths
- After regen, the diff of `*.pb.go` files should be small and mechanical (path renames). A large semantic diff usually means an old `buf.gen.yaml` template was used — verify each tier's gen template was invoked.

### Phase 6 — Cleanup

Only after build is green and tests pass:

```bash
# List what's about to be deleted (sanity check)
find internal/ models/ handlers/ -type d -empty 2>/dev/null

# Then delete
find internal/ models/ handlers/ -type d -empty -delete 2>/dev/null
```

Scope `find` to the **old roots** explicitly — never run it from the repo root unscoped, or you'll delete empty dirs the user wanted to keep (e.g., placeholder `examples/`).

If a top-level dir is now empty (`internal/`, `pkg/`, `models/`), `git rm -r` it.

### Phase 7 — Verify

```bash
go build ./...
go vet ./...
go test ./...
git status            # there should be no untracked .go files in the old layout
git diff --stat HEAD~N..HEAD  # sanity check — N = number of batch commits
```

If the project has supervisord, also confirm `supervisord.conf` paths still match `engine/*/`. If it has `Makefile` targets that point to old paths (build outputs, proto dirs, migration dirs), update those too — they're easy to miss because `go build` doesn't read them.

## Ambiguous Cases — How to Decide

**`handlers/` could be controllers or REST gateway.** Look at the imports:
- Imports `*pb.go` types and registers via `RegisterXxxServer` → gRPC controller → `engine/grpc/controller/`
- Imports `net/http`, uses `http.HandlerFunc` / `mux.Router` directly → REST handler → `engine/rest/` (and consider whether it should be replaced by grpc-gateway)

**Mixed-layer files** (e.g., a "service" file that has SQL queries inline). Split before moving:
- Pull the DB code into a new repository file under `src/repository/`
- Leave the orchestration in the service file
- Then move both into their respective targets

**`pkg/` is the hardest dir** because Go projects use it for everything. Per-file decision:
- Internal helpers used only by this service → `src/helpers/`, `src/constant/`, `src/logger/`, etc.
- Value types (no behavior, just data shapes) → `src/model/types/`
- gRPC client SDK *exposed for other services* → `integration/{tier}/v1/`
- Truly generic, reusable across services → flag to the user; they probably want it in a shared module, not in this service

**API tier (admin / insider / public).** If the existing project doesn't distinguish tiers, default everything to `admin/` and ask the user which routes should be `insider` (back-office tools) or `public` (customer-facing). Don't guess from route paths — auth requirements decide this, not URLs.

## When to Split Into Multiple PRs

If the repo has >50 Go files or >5 domains, suggest splitting:

- **PR 1**: Scaffold target dirs (empty), move shared infra (config, logger, constant, helpers). Low-risk, no business-logic changes.
- **PR 2**: Entities, types, frame DTOs. Mechanical moves.
- **PR 3**: Repositories. Touches DB code — reviewable on its own.
- **PR 4**: Services. The biggest semantic move.
- **PR 5**: Proto + regenerate. Often touches every package via import updates.
- **PR 6**: Controllers, transformers, Wire. Wires it all together.
- **PR 7**: Cleanup — delete old dirs, update Makefile, supervisord.conf, CI configs.

Smaller PRs make review tractable and let bisect find the breaking move quickly.

## What Not to Do

- ❌ **Don't `cp -r` then leave the originals.** This is the failure mode this whole doc exists to prevent.
- ❌ **Don't bulk-`sed` imports across the repo without reading the diff.** Module-internal imports look similar enough that you'll accidentally rewrite something you didn't mean to.
- ❌ **Don't move generated files.** Regenerate them.
- ❌ **Don't reformat / lint-fix in the same commit as a move.** It hides the actual move in a sea of whitespace changes.
- ❌ **Don't run `find . -type d -empty -delete` from the repo root unscoped.** Always pass the old-layout dirs explicitly.
- ❌ **Don't delete files the user didn't authorize.** Flag and ask. Orphaned-looking files often aren't.
- ❌ **Don't promise a single-PR restructure on a large codebase.** Suggest the split.
